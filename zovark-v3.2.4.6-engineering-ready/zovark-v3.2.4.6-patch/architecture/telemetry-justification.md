# Telemetry Field Justification

**Required by:** ADR-0041 §field-justification-document.
**Owners:** control-plane-owner, security-officer.
**Update process:** any addition to this file requires ADR-0041 amendment + 30-day customer notice + opt-out window before activation. `[policy-commitment:product-owner,release-review]`
**Implementation status:** Field rationale exists now. Runtime telemetry audit log, preview command, and emitter allowlist gate are M2 deliverables.

## Purpose

This document is the per-field rationale for every entry on the `telemetry_envelope.schema.json` allowlist. Its job is to make adding a new field **expensive on purpose** — every "let's just add one more metric" request from M2 onward must justify itself here.

If a field is not in this document, it must not appear in `telemetry_envelope.schema.json`. If it is in `telemetry_envelope.schema.json` but not here, the future release-metadata gate must fail. That gate is post-apply baseline work and is not present in this patch tree.

## Field-by-field

### `envelope_version`

- **Why:** Allows customer instances and the Control Plane to reject incompatible telemetry envelopes before reading payload fields.
- **Format:** Schema-level envelope version string.
- **Reversibility:** None.
- **Forbidden replacement:** Runtime version or bundle version.

### `instance_pseudonym`

- **Why:** Allows control plane to recognize the same customer instance across sessions without learning the customer identity.
- **Format:** `pseudo-` followed by 32 hex chars (128 bits of cryptographic random; per-instance; assigned at first registration). `[policy-commitment:security-officer,release-review]`
- **Reversibility:** Only by Zovark with elevated role + audit log entry per ADR-0038. Customer-name → pseudonym mapping is per-row encrypted with a key separate from the registry's master key.
- **Can the customer disable:** No. Always present in any non-`disabled` mode. (In `disabled` mode, no telemetry is sent, so the pseudonym does not leave the customer environment.)
- **Forbidden replacement:** Customer name, customer ID, hostname, IP address, MAC address, license key. None of these may substitute for the pseudonym, ever.

### `sent_at`

- **Why:** Provides customer-auditable ordering and freshness for outbound telemetry.
- **Format:** RFC 3339 timestamp.
- **Reversibility:** None.
- **Forbidden replacement:** Investigation timestamp, alert timestamp, host timestamp, or audit-event timestamp.

### `payload_kind`

- **Why:** Binds the envelope to one explicitly enumerated payload shape and lets contract checks reject mismatched `(payload_kind, payload)` pairs.
- **Format:** Enum: `status`, `health`, `failure_signature`, `none`.
- **Reversibility:** None.

### `payload`

- **Why:** Carries one of the allowlisted payload shapes. The allowed fields depend on `payload_kind`.
- **Format:** Object bound by `telemetry_envelope.schema.json`.
- **Forbidden replacement:** Arbitrary JSON, raw logs, stack traces, investigation evidence, customer identifiers.

### `customer_audit_id`

- **Why:** Correlates the outbound payload to the customer's future local telemetry audit-log row without exposing audit-log contents.
- **Format:** UUID.
- **Reversibility:** None without customer-side audit-log access.
- **Forbidden replacement:** Audit event body, audit chain root, or customer ticket ID.

### `bundle_version`

- **Why:** Required for compatibility-matrix lookup; control plane must know which bundle to recommend as the next update.
- **Format:** Semantic version string (`v3.2.4.2`).
- **Reversibility:** None.
- **Can the customer disable:** Yes (mode=`disabled`); no in other modes.
- **Forbidden replacement:** None.

### `schema_version`

- **Why:** Determines compatible Wazuh→OCSF mapping versions and signed-bundle compatibility.
- **Format:** Semantic version string.
- **Reversibility:** None.
- **Can the customer disable:** Yes (mode=`disabled`).

### `feature_registry_version`

- **Why:** Tells control plane which feature set this instance is on. Used to suppress recommendations for features the instance has explicitly rejected (e.g., F-006).
- **Format:** Semantic version string.
- **Reversibility:** None.

### `adapter_versions`

- **Why:** Some updates are adapter-specific. Wazuh adapter v1.2 → v1.3 may be safe but v1.3 → v2.0 may require a customer config change.
- **Format:** Object mapping adapter name → version string.
- **Reversibility:** None.
- **Forbidden replacement:** Adapter installation paths, adapter config files, adapter logs.

### `tool_catalog_version`

- **Why:** Tools generated by the Research Pipeline are versioned as a catalog; control plane needs to know which catalog version this instance has.
- **Format:** Semantic version string.

### `health_status`

- **Why:** Allows control plane to identify struggling instances and prioritize patches for their specific failure modes.
- **Format:** Enum: `healthy`, `degraded`, `critical`.
- **Reversibility:** None.
- **Forbidden replacement:** Specific failure messages, stack traces, log lines, customer-specific component names.

### `last_successful_replay_timestamp`

- **Why:** Replay determinism is core to the trust contract (INV-005). If an instance has not successfully replayed in 30+ days `[policy-commitment:support-owner,quarterly-review]`, control plane flags it for support outreach.
- **Format:** RFC 3339 timestamp.
- **Forbidden replacement:** Investigation IDs, replay record content, replay duration, replay subject.

### `last_audit_chain_verification_timestamp`

- **Why:** Same as above, for audit-chain integrity (INV-016).
- **Forbidden replacement:** Audit log content, audit chain root hashes.

### `last_update_applied_version`

- **Why:** Allows control plane to know whether the customer is current. Combined with `failed_update_attempts_count`, identifies stuck customers.

### `failed_update_attempts_count`

- **Why:** If an update has failed multiple times for an instance, support outreach is triggered. Without this metric, stuck customers go silent.
- **Format:** Non-negative integer.
- **Forbidden replacement:** Failure messages, update-specific error codes, root cause analysis.

### `topology_mode`

- **Why:** Some updates are mode-specific (e.g., air-gap mode may receive a smaller bundle that excludes online-only features).
- **Format:** Enum: `saas`, `hybrid`, `air-gap`.
- **Positioning note:** Telemetry mode and topology choice are independent of
  the buying wedge. Per ADR-0052, deterministic replay and evidence integrity
  are the primary differentiator; air-gap remains a supported topology option.

### `disabled_capabilities`

- **Why:** Customer may disable specific capabilities (e.g., turn off Sigma generation). Control plane should not recommend updates for disabled capabilities.
- **Format:** Array of capability identifiers.

### `signature_hash`

- **Why:** Lets the Control Plane group repeated failure classes without receiving the failing data, stack trace, file path, hostname, or tenant identifier.
- **Format:** 64 lowercase hex chars; salted per customer instance.
- **Reversibility:** Not reversible by the Control Plane because the salt never leaves the customer instance.
- **Forbidden replacement:** Raw exception, stack trace, log message, file path, alert content, or host identifier.

### `component`

- **Why:** Identifies the coarse subsystem that produced a failure signature so support can route remediation.
- **Format:** Enum from `telemetry_envelope.schema.json`.
- **Forbidden replacement:** Specific process name, host path, container ID, or customer-defined component name.

### `occurred_at`

- **Why:** Captures when a failure signature occurred without sending incident evidence.
- **Format:** RFC 3339 timestamp.
- **Forbidden replacement:** Alert timestamp, investigation timestamp, or user activity timestamp.

## Forbidden fields (no exception, no opt-in)

These fields are **never** added to the allowlist regardless of customer request, support need, or telemetry-tooling convenience. Anyone proposing to add one of these has misunderstood the trust contract:

- Raw alerts
- Investigation evidence
- Tenant secrets
- EDR credentials
- Audit log entries
- Replay records
- Customer PII
- Customer hostnames
- Customer IPs (other than synthetic test ranges)
- Specific Sigma rules deployed
- Customer-defined templates
- EDR action history
- Vault audit entries
- Healer findings
- Mesh investigation summaries
- Customer license keys
- Customer billing identifiers
- User counts
- Tenant counts within an instance
- Specific failure messages or stack traces
- Investigation outcomes (verdicts)
- Specific filenames or paths from the customer environment

## Audit log

Future M2 runtime behavior: every outbound telemetry payload writes a record to `<customer-instance>/var/log/zovark/telemetry_audit_log.jsonl`. The log is append-only, hash-chained, and customer-readable. Planned operations:

```bash
tail -f /var/log/zovark/telemetry_audit_log.jsonl
zovark telemetry diff --since "1h ago"
zovark telemetry verify-audit-log
zovark telemetry preview
```

## Salt management

For any field whose value is a hashed input (e.g., `signature_hash` in a `failure_signature` payload), the salt is generated **per customer instance** at first install and **never leaves the customer environment**. The control plane therefore cannot reverse the hash to recover the input even with full corpus access.

Salt rotation: every 12 months, or on suspicion of compromise. `[policy-commitment:security-officer,quarterly-review]` Salt rotation does not break historical telemetry (each payload includes the salt epoch).
