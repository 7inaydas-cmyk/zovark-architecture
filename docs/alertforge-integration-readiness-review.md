# AlertForge Integration Readiness Review

Status: integration readiness review. This document does not connect AlertForge,
add live integrations, add tests, create customer-readiness material, start
outreach, add legal/certification claims, or change adapter/verifier behavior.

## Definition

AlertForge is the user's synthetic alert and scenario generator.

AlertForge is not Zovark architecture. It should be treated as an upstream
scenario source that can produce deterministic, sanitized alert/scenario inputs
for Zovark validation.

Zovark remains responsible for:

- ingesting or adapting the scenario output
- generating Proof Package V1 or explicit Proof Package V2
- verifying generated packages offline
- preserving evidence boundaries and limitations

## Current Readiness

Current repo support is limited to an AlertForge-style static fixture:

- `tests/fixtures/v3-realistic-scenarios/alertforge-style-ransomware-containment.json`
- `tests/test_v2_realistic_scenario_validation.py`

That fixture is useful as a validation gate. It is not a live AlertForge
integration, customer demo, product workflow, or benchmark.

## Expected AlertForge Output Contract

Before integration, AlertForge should produce a deterministic, sanitized JSON
fixture or scenario directory with these classes of data:

- Stable scenario identifier.
- Stable tenant or environment reference.
- Alert envelope:
  - `alert_id`
  - deterministic timestamp
  - alert type
  - host or asset identifier
  - severity
  - source process / child process when relevant
- Execution envelope:
  - `execution_mode`: `tools`, `sandbox`, or `sandbox_fallback`
  - `source`: saved plan, LLM-selected tools, template, generated, or fallback
    vocabulary accepted by the adapter
  - `path_taken`
  - `plan_executed`
  - tool names and deterministic tool result summaries
  - verdict/final decision where supplied
  - governance decision where supplied
- Evidence arrays:
  - process events
  - network events
  - credential access events
  - lateral movement events
- Optional practitioner context:
  - context enrichment
  - visibility gaps
  - approval/governance metadata
  - blast-radius evidence
  - rollback evidence
  - controls snapshot evidence
  - safe trace metadata
- Leak-sensitive fields must be absent or sanitized:
  - raw prompts
  - raw tool arguments
  - raw tool outputs
  - payload bodies
  - chat messages
  - analyst/model notes
  - hidden reasoning
  - chain-of-thought

All timestamps must be scenario-recorded values, not values generated by replay.
No local absolute paths, host metadata, randomness, or live-service handles should
be required.

## Zovark Ingest Requirements

Current adapter requirements:

- Fixture must be an object.
- Alert must contain `alert_id` and a deterministic timestamp.
- Execution must contain a supported `execution_mode`.
- Event arrays, when present, must be lists of objects.
- Declared top-level and nested verdicts must not conflict with the derived
  Slice proof verdict.
- V2 generation must be explicit through `proof_package_version=V2_PACKAGE_CONTRACT`.
- Source refs in V2 objects must resolve through verified V1 evidence.
- V2 conditions must match conditions derived by the verifier from verified
  evidence.
- Default V1 generation must remain V1-only.

Current generation entry point:

```python
write_proof_package_from_v3_fixture(
    fixture,
    output_dir,
    proof_package_version=V2_PACKAGE_CONTRACT,
)
```

Current verification entry point:

```python
verify_proof_package(output_dir)
```

## Integration Unknowns

Before building the integration, resolve:

- Does AlertForge output one scenario JSON file, multiple evidence files, or a
  directory bundle?
- Which fields are guaranteed stable versus optional?
- Does AlertForge generate already-sanitized prompt/tool metadata, or must Zovark
  reject unsafe fields at ingest?
- How are scenario-generated source refs represented?
- How should multi-alert or multi-host scenarios map into one proof package?
- Which action vocabulary will AlertForge emit, and how does it map to current
  verified action vocabulary such as `isolate_host`?
- How are controls snapshots represented, and how are metadata-only values
  distinguished from actual control evidence?
- How are visibility gaps represented without implying full visibility?
- Does AlertForge need a schema version?
- Should Zovark accept AlertForge outputs directly or through a normalization
  command?
- What should the local output directory lifecycle be?

## Readiness Risks

- Current realistic validation covers one static scenario. More scenarios are
  needed before broad confidence.
- V2 proof package verification proves package consistency, not that AlertForge
  produced complete or realistic upstream evidence.
- Current adapter supports representative fixtures, not a formally versioned
  AlertForge schema.
- AlertForge must not be allowed to bypass V2 source-ref resolution or condition
  derivation.
- AlertForge output must not become a customer-readiness package by accident.

## Recommended Integration Boundary

The smallest safe integration boundary is:

```text
AlertForge deterministic sanitized scenario JSON
-> Zovark normalization/validation
-> explicit V2 package generation
-> offline Replay verification
-> leak and determinism checks
```

The first integration PR should avoid live services, benchmarks, customer-demo
artifacts, signing/anchoring, legal claims, certification claims, and outreach.
