# Investigation Trace V1

Status: documentation/spec PR only. This document defines the Investigation Trace
V1 record model. It does not add runtime code, proof-package schema changes,
fixture files, V3 adapter code, Replay V2 behavior changes, live connectors,
Capability Gateway runtime, or manifest/provenance/signing implementation.

## Purpose

Investigation Trace V1 records how a V3 investigation moved from input alert to
candidate findings, accepted findings, rejected findings, governance outcome, and
proof-facing artifacts.

The trace exists to preserve the distinction between:

- deterministic tools selected by a saved plan
- tools selected by an LLM
- V2 sandbox/codegen fallback after tool-runner failure
- explicit sandbox mode
- policy/governance decisions
- institutional knowledge and correlation context
- visibility gaps and coverage assumptions

Investigation Trace V1 is the bridge between V3 runtime evidence and the
Capability Identity Contract. The trace records ordering and relationships. The
Capability Identity Contract records stable identities, versions, sources, modes,
policies, and hashes for the capabilities referenced by those records.

## Non-Goals

Investigation Trace V1 does not:

- call live EDR, SIEM, LLM, DB, network, dispatcher, Vault runtime, or external
  systems during replay
- prove legal admissibility
- prove production forensic completeness
- prove that all relevant upstream evidence was collected
- replace Vault authorization
- replace the approval-required proof handoff
- define Fast Mode or Reasoning Mode product modes
- add manifest/provenance/signing
- change the current nine-file proof-package contract
- implement the V3-to-proof adapter

## Trace Container

A future trace export should be a deterministic object with this shape:

| Field | Required | Meaning |
| --- | --- | --- |
| `trace_version` | yes | Fixed value for this spec, e.g. `investigation-trace-v1`. |
| `trace_id` | yes | Deterministic identifier for the trace. |
| `investigation_id` | yes | Stable investigation or task identifier from the producing system. |
| `source_refs` | yes | Repository, commit, package, fixture, or runtime references used to produce the trace. |
| `capture_status` | yes | `complete`, `partial`, or `degraded`. PR #28 evidence implies `partial` for many V3 cases. |
| `records` | yes | Ordered list of trace records. |
| `trace_hash` | yes | Deterministic hash of the canonical trace with `trace_hash` blanked or null. |

The trace must not include absolute local paths, host-specific metadata, random IDs,
or wall-clock values generated by replay. Runtime timestamps may be preserved only
when they are part of the recorded source output; replay must not generate new ones.

## Common Record Fields

Every trace record must contain:

| Field | Required | Meaning |
| --- | --- | --- |
| `record_id` | yes | Deterministic identifier for this record. |
| `record_type` | yes | One of the record types defined below. |
| `record_version` | yes | Version of the record shape. |
| `sequence` | yes | Strictly increasing integer starting at 1. |
| `stage` | yes | Producing stage, such as `ingest`, `analyze`, `execute`, `assess`, `govern`, `store`, or `proof_adapter`. |
| `capability_refs` | yes | List of Capability Identity Contract `capability_id` values. Empty only when PR #28 found no grounded capability identity. |
| `input_refs` | yes | Record IDs, evidence IDs, or source refs consumed by this record. |
| `output_refs` | yes | Record IDs, finding IDs, evidence IDs, or package refs produced by this record. |
| `input_hash` | yes | Canonical hash of the recorded input envelope or `null` if not captured. |
| `output_hash` | yes | Canonical hash of the recorded output envelope or `null` if not captured. |
| `status` | yes | `succeeded`, `failed`, `skipped`, `not_captured`, or `unknown`. |
| `capture_status` | yes | `captured`, `not_captured`, `unknown`, `deferred`, or `not_applicable`. |
| `record_hash` | yes | Canonical hash of the record with `record_hash` blanked or null. |

Optional common fields:

| Field | Meaning |
| --- | --- |
| `source_ref` | Path, commit, fixture, or runtime source of the record. |
| `parent_record_ids` | Records this record logically depends on. |
| `notes` | Bounded human-readable explanation. Must not add evidence not present in the structured fields. |
| `missing_fields` | Fields expected by this spec but absent from the fixture/runtime source. |

## Record Ordering

Records are ordered by `sequence`, not by wall-clock time.

Ordering rules:

1. `sequence` starts at 1 and is strictly increasing.
2. A record may reference only earlier records in `input_refs` and
   `parent_record_ids`.
3. `record_hash` must be stable regardless of object key order.
4. Replay must reject duplicate `record_id` values.
5. Replay must reject references to unknown record IDs, evidence IDs, finding IDs,
   or capability IDs.
6. Missing runtime fields must be represented as `not_captured`, `unknown`,
   `deferred`, or `not_applicable`; they must not be silently fabricated.

## Record Types

### `ingest_record`

Records the alert or investigation input accepted by the runtime.

Required fields:

- common record fields
- `source_type`
- `tenant_ref`
- `task_type`
- `alert_hash`
- `raw_input_ref` or `raw_input_hash`

Optional fields:

- `task_id`
- `trace_id`
- `pii_masked`
- `pii_entity_map_key`
- `skill_id`
- `skill_template`
- `skill_params`
- `skill_methodology`

Capability mapping:

- If the runtime has an ingest capability identity, include it in
  `capability_refs`.
- If no ingest capability identity exists, set `capability_refs: []` and
  `capture_status: not_captured`.

- `IngestOutput` fields exist in code.
- Saved-plan unit fixtures did not capture full ingest metadata.

### `dedup_decision_record`

Records whether the alert was deduplicated or linked to an earlier alert.

Required fields:

- common record fields
- `dedup_status`: `new`, `duplicate`, `not_checked`, or `unknown`
- `duplicate_of`
- `dedup_reason`

Optional fields:

- `dedup_key_hash`
- `dedup_policy_ref`

Capability mapping:

- Map policy-backed dedup to a Capability Identity Contract record with
  `capability_type: governance_policy` or a future policy capability type.
- If no policy identity exists, record the decision and mark capability identity as
  `not_captured`.

PR #28 status:

- Dedup code exists, but saved-plan fixtures did not capture the decision.

### `batching_record`

Records alert batching or grouping decisions before analysis.

Required fields:

- common record fields
- `batch_id`
- `batch_decision`: `batched`, `single`, `not_checked`, or `unknown`
- `batch_member_refs`

Optional fields:

- `batch_policy_ref`
- `batch_key_hash`

Capability mapping:

- Map policy-backed batching to a policy capability identity when available.

PR #28 status:

- Batching evidence was not captured.

### `plan_selection_record`

Records how the investigation plan was selected.

Required fields:

- common record fields
- `selection_source`: `saved_plan`, `db_saved_plan`, `llm_selected`, `template`,
  `fallback`, or `unknown`
- `execution_mode`: `tools`, `sandbox`, or `sandbox_fallback`
- `plan_id`
- `plan_hash`
- `plan_steps_hash`

Optional fields:

- `path_taken`
- `skill_id`
- `selection_model_record_id`
- `prompt_hash`
- `prompt_version`
- `fallback_reason`

Capability mapping:

- Saved built-in plan: `capability_type: plan`, `source: builtin`,
  `execution_mode: tools`.
- DB saved plan: `capability_type: plan`, `source: db_saved`,
  `execution_mode: tools`.
- LLM-selected tool path: reference a preceding `model_invocation_record` and a
  capability with `source: llm_selected`.
- Sandbox or fallback plan: reference the generated/template/fallback capability.

### `model_invocation_record`

Records an LLM call used to select tools, generate code, or produce other runtime
output.

Required fields:

- common record fields
- `model_ref`
- `prompt_hash`
- `prompt_version`
- `response_hash`
- `recorded_io_ref`

Optional fields:

- `tokens_in`
- `tokens_out`
- `latency_ms`
- `provider_ref`
- `temperature`
- `tool_selection_hash`
- `error_message_hash`

Capability mapping:

- Map to `capability_type: model_invocation`.
- Use `source: llm_selected` for tool selection.
- Use `source: generated` for code generation.

- Replay never calls the model.

### `tool_call_record`

Records one deterministic tool call and its recorded output.

Required fields:

- common record fields
- `tool_name`
- `tool_version`
- `tool_catalog_ref`
- `arguments_hash`
- `tool_output_hash`
- `tool_status`: `succeeded`, `failed`, `skipped`, or `unknown`

Optional fields:

- `tool_result_ref`
- `error_hash`
- `timeout_ms`
- `selected_by_record_id`
- `plan_selection_record_id`

Capability mapping:

- Map to `capability_type: tool`.
- `source` is usually `builtin`.
- `parameter_source` depends on the plan source: `system`, `human`, `model`,
  `template`, or `policy`.

Replay rule:

- Replay never invokes the live tool.

### `candidate_finding`

Records a proposed finding before deterministic acceptance or rejection.

Required fields:

- common record fields
- `candidate_finding_id`
- `finding_text_hash`
- `proposed_by_record_ids`
- `evidence_refs`
- `confidence`

Optional fields:

- `model_contribution`

Capability mapping:

Replay rule:

### `accepted_finding`

Records deterministic acceptance of a candidate finding into proof-facing findings.

Required fields:

- common record fields
- `accepted_finding_id`
- `candidate_finding_id`
- `acceptance_rule_ref`
- `evidence_refs`
- `proof_finding_ref`

Optional fields:

- `normalization_hash`
- `acceptance_reason`

Capability mapping:

- Reference the deterministic synthesis capability or rule identity when available.

Replay rule:

- Proof-package findings may be derived only from accepted findings or current Slice
  deterministic rules. Rejected findings must not appear as proof findings.

### `rejected_finding`

Records deterministic rejection of a candidate finding.

Required fields:

- common record fields
- `rejected_finding_id`
- `candidate_finding_id`
- `rejection_rule_ref`
- `rejection_reason`

Optional fields:

- `conflicting_record_ids`
- `missing_evidence_refs`

Capability mapping:

- Reference the deterministic synthesis capability or rule identity when available.

Replay rule:

- Replay verifies that rejected findings are excluded from proof findings.

### `governance_decision`

Records observe/assist/autonomous governance evaluation.

Required fields:

- common record fields
- `autonomy_level`: `observe`, `assist`, `autonomous`, or `unknown`
- `needs_human_review`
- `review_reason`
- `policy_ref`
- `verdict_ref`

Optional fields:

- `governance_config_hash`
- `tenant_ref`
- `task_type`

Capability mapping:

- Map to `capability_type: governance_policy`.

### `visibility_gap`

Records known missing visibility that affects investigation confidence or scope.

Required fields:

- common record fields
- `gap_id`
- `gap_type`
- `description`
- `affected_records`
- `impact`: `low`, `medium`, `high`, or `unknown`

Optional fields:

- `requested_evidence`
- `blocking_reason`
- `workaround`

Capability mapping:

- Usually no direct capability identity. If generated by a tool or model, reference
  that capability.

Replay rule:

- Replay verifies that visibility gaps were recorded. Replay does not close or
  repair gaps.

### `coverage_assumption`

Records a bounded assumption used by the investigation or proof adapter.

Required fields:

- common record fields
- `assumption_id`
- `assumption_text`
- `scope`
- `basis`: `fixture`, `policy`, `operator_input`, `runtime_default`, or `unknown`

Optional fields:

- `risk_if_false`
- `expiration_condition`

Capability mapping:

- Reference policy or operator-input capability if available.

Replay rule:

- Replay can verify that the assumption was recorded. Replay does not prove the
  assumption is true.

## Path Representation

### Saved-Plan Deterministic Path

Minimum record order:

1. `ingest_record`
2. optional `dedup_decision_record`
3. optional `batching_record`
4. `plan_selection_record` with `selection_source: saved_plan` or
   `db_saved_plan`
5. one or more `tool_call_record` entries
6. one or more `candidate_finding` records
7. `accepted_finding` and `rejected_finding` records
8. `governance_decision`

No `model_invocation_record`, `generated_code_record`, `ast_validation_record`, or
`sandbox_execution_record` is required for this path unless the source fixture shows
one.

### LLM-Selected Tool Path

Minimum record order:

1. `ingest_record`
2. `model_invocation_record`
3. `plan_selection_record` with `selection_source: llm_selected`
4. one or more `tool_call_record` entries referencing the model-selected plan
5. candidate/accepted/rejected finding records
6. `governance_decision`

Replay verifies the recorded model response and selected plan. Replay never calls
the model.

### Tool-Runner Error With Sandbox Fallback

Minimum record order:

1. records for the original tools path
2. failed `tool_call_record` or failed plan execution record
3. `generated_code_record` if fallback generated or reused code
4. `ast_validation_record`
5. `sandbox_execution_record` with `execution_mode: sandbox_fallback`
6. candidate/accepted/rejected finding records from recorded fallback output

The trace must preserve the fallback transition and reason. The V3-to-proof adapter
must not present sandbox fallback as ordinary deterministic tool execution.

### Explicit Sandbox Mode

Minimum record order:

1. `ingest_record`
2. `generated_code_record` or template code record
3. `ast_validation_record`
4. `sandbox_execution_record` with `execution_mode: sandbox`
5. candidate/accepted/rejected finding records
6. `governance_decision`

Explicit sandbox mode must remain distinguishable from Path D fallback.

### Context Lookups

Institutional knowledge and correlation history must be recorded as inputs:

- institutional knowledge uses `context_lookup` capability identity and usually
  `parameter_source: human` or `system`
- correlation history uses `context_lookup` capability identity and usually
  `parameter_source: system`

If DB-backed context is not captured, the record must say `capture_status:
not_captured` or `unknown`; it must not claim context was replay-verified.

## Missing Fields From PR #28

PR #28 did not capture all required future trace fields. Trace V1 handles this by
making missing evidence explicit:

| Missing Evidence | Trace Handling |
| --- | --- |
| full Path C runtime output | Record `model_invocation_record` and downstream outputs only when captured; otherwise mark as `not_captured`. |
| full real Path D output | Record fallback transition from static evidence; mark code/sandbox output fields as `not_captured` until captured. |
| full explicit Docker sandbox output | Record route/policy evidence; mark stdout/stderr/code hashes as `not_captured` until captured. |
| all governance modes over one shared payload | Record observed mode fixtures; mark missing modes as `not_captured`. |
| DB-backed institutional knowledge fixture | Record lookup shape; mark DB-backed payload as `not_captured`. |
| DB-backed correlation history fixture | Record lookup shape; mark DB-backed payload as `not_captured`. |
| durable per-tool call record table | Use exported trace `tool_call_record` entries later; current repo evidence does not prove a durable table exists. |
| customer/SOC-reviewed fixture | Mark validation status as `unknown` or `not_captured`. |

Unknowns and gaps must be visible in the trace through `visibility_gap` or
`coverage_assumption` records where they affect findings, verdict, or proof
confidence.

## Replay Verification Semantics

Replay verifies recorded outputs. It does not execute investigation behavior.

Replay should verify:

- trace container hash
- record ordering and unique IDs
- `record_hash` for each record
- all input/output hashes
- references to capabilities, records, evidence, and findings
- model invocation hashes without calling the model
- tool call outputs without calling the tool
- generated/scrubbed code hashes without executing code
- AST validation result as recorded output, not by rerunning validation
- sandbox stdout/stderr hashes without running a sandbox
- candidate finding acceptance/rejection consistency
- proof findings derive from accepted findings
- rejected findings are excluded from proof findings
- visibility gaps and coverage assumptions are preserved
- deterministic proof-package outputs can be rederived from accepted trace content

Replay does not prove:

- legal admissibility
- certification readiness
- cryptographic signing unless a later signing layer exists
- transparency-log anchoring unless a later anchoring layer exists
- completeness of upstream evidence collection
- truth of external systems not captured in the package
- current live state of EDR, SIEM, DB, or model services
- that a coverage assumption is true

## Proof-Package Schema Bump Gate

A proof-package schema bump is required if product requirements demand first-class
export or verifier support for any of these beyond what the current nine-file
package can represent without ambiguity:

- Investigation Trace V1 as a package artifact
- recorded model/tool invocation records
- candidate, accepted, and rejected findings
- visibility gaps
- coverage assumptions
- sandbox fallback provenance
- explicit sandbox execution provenance
- plan/tool implementation identities
- DB-backed context provenance
- runtime governance records separate from proof handoff approval

A schema bump is not required merely to write this spec. Any future schema change
must be a separate PR with explicit package-contract updates and verifier tests.

## Acceptance Criteria For Future Implementation

Before a runtime trace implementation can merge, it must show:

- every trace record has stable IDs and hashes
- saved-plan, LLM-selected, sandbox fallback, and explicit sandbox paths remain
  distinguishable
- missing fields are explicit and not silently repaired
- model and tool outputs are recorded before proof synthesis
- replay validates recorded outputs without live calls
- proof findings can be traced to accepted findings
- rejected findings remain visible but do not become proof findings
- visibility gaps and coverage assumptions are exported when they affect proof
  interpretation

Before a V3-to-proof adapter can merge, it must show:

- adapter input conforms to this trace spec or explicitly documents unsupported
  fields
- deterministic proof outputs remain replay-verifiable
- existing Replay V2 package verification still fails closed on tampering
